# 对抗式收口（Adversarial closure）

Review 默认立场：**假设 execute 的修复/结论有问题**，再找证据推翻或坐实。  
「当前绿」≠「本批契约闭合」≠「阶段根因闭合」≠「可重复交付」。本文件展开维度 10；SKILL.md 只留裁决规则。

## 立场（必守）

1. **不信自报**：execute 报告、口头「已修好」、单次探测绿 → 待证假说。
2. **先假设修复错了**：问「什么情况下这刀会害人 / 会复发 / 会误导后人」。
3. **分层写结论**（禁止揉成「修好了」）：
   - **当前绿**：此刻与本批相关的探测通过
   - **本批契约闭合**：子 plan 本批 Spec/验收点/Invariant **子集**已满足（允许阶段根因留到后续批）
   - **阶段根因闭合**：总纲「根因分析」里点名的根因已消掉（通常末批或专责批才要求）
   - **可重复交付**：该变更所属域的 SSOT 能让他人重建同一健康态（见下「SSOT 域」）
4. **未证即未完成**：子 plan 写了但没跑的验收点 → 「未证」，不得写本批 PASS。

## 何时适用 / 何时 N/A

| 本批宣称或触及 | 维度 10 |
|----------------|---------|
| 修 bug / 恢复故障 / 宣称 Inv 或验收 PASS / 「Batch done」含行为闭环 | **必做**（按下表追问） |
| 纯契约/逻辑批，无运维手改、验收以单测+契约为主 | 必做，但 C/H 等运维题可 `N/A（本批无运行时入口）` |
| 纯 docs / 文案 / lockfile / 常量、无行为与故障宣称 | 整节 `N/A（理由）`，不得省略标题 |

**禁止**：用「硬门槛不能 N/A」把 UI 改文案批逼去答 CNI/装机题。  
**也禁止**：有故障修复宣称却整节 N/A。

## 「根因」操作定义（防无限上溯）

- **本批根因** = 本批子 plan Spec / 总纲根因表里**本批负责**的那一行（或本批 commit message 自称修的那条）。
- **阶段根因** = 总纲根因分析全表。
- Review 不要求追查「宇宙第一因」；但若 execute 把**症状修补**写成「根因已修」，而总纲/子 plan 写的根因未动 → 打回用词或补做。

## 「可重复交付」按 SSOT 域（勿写死 git+装机）

问：变更落在哪一类权威源？该类能否让别人重建？

| 变更域 | 可重复交付 ✅ 的典型 SSOT | ❌ 信号 |
|--------|-------------------------|--------|
| 应用代码/契约 | git commit + 可复现测试/构建 | 只改了运行中的容器/进程 |
| 集群声明式配置 | git 内 manifest/Helm/脚本，经既定 apply 通道 | 仅集群内 `kubectl/calicoctl patch`，无 git |
| 密钥/凭证 | 文档化的注入路径（Secret 生成脚本、vault 流程）；真值本身可不进 git | 口头告诉别人「我 curl 打进去了」 |
| 节点/OS 基线 | 装机脚本 / cloud-init / 库存文档 | 仅 ssh 手改一台 |
| 纯文档 | git 内 md | —（通常整节 N/A） |

一句话：**可重复 = 对应该域的 SSOT，不是「必须装机脚本」**。无集群的批次不要用「装机」当否决词。

## 强制问题清单（batch，按适用勾选）

对每个「本批宣称修好/通过」的项：

| # | 问题（域中立） | 打回信号 | 常见 N/A 理由 |
|---|---------------|----------|---------------|
| A | **本批根因还是症状？** 相对子 plan/总纲本批行，改的是点名根因还是下游表象？ | 症状修补却写「根因已修」 | — |
| B | **权威状态在哪？** 见上表 SSOT 域 | 只改了非 SSOT 的活状态 | 纯 docs |
| C | **生命周期后还在吗？** 对该域有意义的重建（重装依赖 / 重部署 / 重启进程 / 新环境）后是否仍成立？ | 依赖「别动这台机器」 | 无运行时产物 |
| D | **本批验收证了什么？** 对照**本批**验收点；子集绿 ≠ 本批全量 | 关键 Inv/脚本未跑却 Batch done | — |
| E | **残留是否诚实？** 已知未修是否 follow-up？有无把「当前绿」写成「阶段全修好」？ | 夸大收口 | — |
| F | **废招是否入正典？** 已证伪步骤是否写进正式 docs 当唯一修法？ | runbook 教抄废招 | 无 docs 变更 |
| G | **会否固化错误？** 把易漂移的瞬时值写进持久配置后，无对齐/校验？ | 持久化瞬时值且无校验 | 无持久配置 |
| H | **验证入口是否本批真实入口？** 是否用调试旁路代替子 plan 假定的用户/调用路径？ | 旁路绿、真实入口未测 | 本批无外部入口 |

## 强制问题清单（plan）

| # | 问题 | 打回信号 |
|---|------|----------|
| P1 | 退出条件是否混淆「当前绿 / 本批闭合 / 阶段根因闭合」？ | 末态 Inv 写成每批都必须宇宙级根因归零 |
| P2 | 运维手改批是否要求对应 SSOT（git 或装机），或明确标「集群一次性、不算代码交付」？ | 白名单无 SSOT 却写 Batch done=阶段闭环 |
| P3 | ADR/否决是否挡住「关鉴权 / 废招当永久修」？ | 无边界，执行者会走捷径 |
| P4 | 半完成态是否写明「本批不解决的阶段根因留给哪批」？ | 每批都暗示「全修好」 |

## 裁决（与「半完成态可发布」对齐）

- **本批通过**：本批契约闭合 ✅，且报告未把阶段根因未闭合说成已闭合；可重复交付按本批 SSOT 域 ✅ 或显式 `N/A`。
- **当前绿，本批未闭合**：本批验收未证完，或仅症状修补却宣称本批根因已修 → 不得写本批「通过」。
- **本批通过，阶段未闭合**：合法（半完成态）；MUST 在对抗式一节写清「阶段根因仍开放 → Batch X」。
- **阶段宣称闭环但阶段根因 ❌ 或关键 Inv 未证** → 不得写阶段/末批「通过」。

## 报告写法

```
对抗式收口：
- 适用：必做 / N/A（理由）
- 当前绿：✅ / ❌（证据）
- 本批契约闭合：✅ / ❌（对照验收点…）
- 阶段根因闭合：✅ / ❌ / ⚠️ 非本批职责（留给 Batch X）
- 可重复交付：✅ / ❌ / N/A（SSOT 域：代码|集群声明|密钥|节点|…；缺口…）
- 未证项：[ … ]
- 残留 follow-up：[ … ]
- 废招风险：无 / 有（…）
```
